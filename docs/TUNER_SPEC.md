## 3. Design decisions (made with the user)

- One HTML table is the only editing surface; columns Variable name, Value, Default, Range for base cars, Description. Local server, Windows batch start.
- Apply installs only; the user starts and closes the game; refused while the game runs; a backup of the previous install every time.
- Each car gets its own copy under an id of the same length as the stock id: `ks_` replaced by `ax_` (`ks_bmw_m3_e46_csl` -> `ax_bmw_m3_e46_csl`). Name: the stock display name from the game's `system\cars.table` (not editable) plus a suffix the user chooses in a field next to it (setting `name_suffix`, default `MY`, 1-30 characters, no control characters (the DEL character included), trimmed, inner runs of spaces collapsed; the game name is the stock name, ONE space and the suffix, so `Supercharged` gives `BMW M3 E46 CSL Supercharged`; the default sorts the car next to the stock one in the game's list; counting `MY` -> `MY 2` -> `MY 3`; a saved legacy `_MY` / `_MY<n>` is read as `MY` / `MY <n>` since 2026-11-15, other saved suffixes are shown as they are, for example `_Drift` as `... _Drift`). The stock cars are never modified. Further modded cars of the same stock car get their own ids and suffixes (section 4c).
- Settings the car does not have are hidden (turbo values on naturally aspirated cars unless a turbo kit is chosen, gears beyond the real count, variant name when the car has none).
- Defaults are always read from the stock car in the game, never typed in. Descriptions in English; "unverified" where the meaning is guessed. Descriptions that open with an official statement repeat facts from the official physics documentation of the game (section 6c), followed by our notes; they do not change the unverified flag, which stays until the setting is tested in the game.
- Registration (brand, year, car classes) and the names in the car list come from the game's own data for that car.

## 4. How a build works

1. `init --car <id>` extracts that car (and its row from `cars.table`, and the shared stock localization once) from the game's `content.kspkg` into `%USERPROFILE%\ace_modded_cars_work\<car id>\base`.
2. Every Apply starts from that pristine copy: clone under the new id by same-length text replacement (no protobuf length changes; the stock id stays after `event:/evo_cars/` and `content\sfx\`, which name the game's engine sound events and bank), add the mod registration and localization, change the chosen settings in every copy of the value (standalone file and the inline copy in the car's `.car`), write the garage tyre selection when the state has one (section 4d), build from the turbo kit tree instead of base when the state has a turbo kit (section 4h), pack, back up the installed package, install.
3. The catalogue names files by role (`@engine`, `@gearbox`, `@drivetrain`, `@brakes`, `@setup`, `@limits`, `@car`, `@mech_preset`, `@turbo[N]`, `@clutch`, `@coilover_front`, `@coilover_rear`, `@tyre_front`, `@tyre_rear`), resolved per car through its `.car` manifest, so one catalogue serves all cars. A setting is applicable when its required targets resolve; inline `.car` copies are optional targets.
4. An Apply with no changes equals a plain clone (tested on all five cars).
5. The catalogue file has the top-level parts `groups` and `settings`. `groups` is the list of the setting groups in display order, each `{name, description}` (description 1 to 360 characters, no control characters, names unique); `load_catalogue` refuses a catalogue in which a setting's group is not listed or a listed group has no setting. Today 18 groups: Meta, Display, Engine, Turbo, Gearbox & clutch (incl. the clutch torque), Differential, Differential (hardware), Steering, Brakes, Vehicle (hardware), Springs & anti-roll, Ride height & bump stops, Dampers, Suspension (physical), Alignment & tyres (incl. caster), Tyres, Fuel, Electronics. A setting may carry the optional flag `advanced` (true or false): the page hides it unless the box "show advanced settings" is ticked or its value is changed; apply ignores the flag. Only `collar_front` and `collar_rear` have it (Kunos: the editor's Auto Setup computes the collar positions, section 6c). Setting ids and saved values did not change with the regrouping.
6. The work folder is outside OneDrive and outside AppData (the Claude desktop app redirects AppData writes into a private folder the user cannot see). Long paths (the Porsche's thumbnails exceed 260 characters) are handled with extended-length paths.
7. What a build reports is the change since the last build of the same modded car (Alex, 2026-11-15). After the package is packed, `apply` compares the build with the snapshot `<work>/<stock car>/snapshots/<new id>.json` (the changed settings with their values, the turbo kit donor, the garage selection, the changed sound slots, the game name, the time), then writes the snapshot of this build (also for `--no-install`; a failed build leaves the old one; a missing or damaged snapshot counts as no previous build). The result key `changes` = `{since: "last build" | null, settings: [{id, from, to}], extras: [{kind: turbo_kit | garage | sound, slot, from, to, text}], total}`; `applied` (every change against the stock car) and `notes` stay as they were. The first build of a car lists everything against the stock car, every later one only the difference (a setting set back to default shows `to` = the stock value). The CLI output and the job log print `tune.change_lines(result)` (count line, one line per setting and extra, then the notes); the page shows a heading line and an open "Changes (N)" list with the settings and then the turbo kit, garage and sound changes. A build that fails at the install step already wrote its snapshot, so the retry shows no change. Duplicate and Create start without a snapshot.

## 4b. Server

`python tools\tuner_server.py [--port N] [--bind <address>] [--work <dir>] [--mods <dir>] [--logs <dir>] [--game <content.kspkg>]` serves `tuner/web/index.html` at `/ACESCT/` (fixed base path; `/ACESCT` redirects with 301, `/` with 302, every other path is 404) on all network interfaces by default (`--bind 127.0.0.1` for local only). Alex's decision (2026-11-13): the page is reachable from phones in the home network, no PIN; the server accepts a request only from a loopback or private IPv4 peer (403 "forbidden client address" otherwise) and only with a Host of the form `<localhost | private or loopback IPv4 | this PC's host name>:<port>` (403 "forbidden host: open the tuner with the address the console prints ..."); every POST still needs the header `X-Tuner: 1` and Content-Type `application/json`. At start it prints the local address and one line per private address of the PC. Windows asks once to allow Python on the private network (default port 8080, `--port` 1024 to 65535; `--game` is the game's `content.kspkg`). Every answer carries `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`; the `Server` header names no Python version. A client that stops sending is dropped after 30 s (`Handler.timeout`). `GET /api/state` asks whether the game runs at most every 15 s (`GAME_CHECK_SECONDS`); Apply always asks again.

| Route | Purpose |
|---|---|
| `GET /ACESCT/` | the page (every route below is served under the prefix `/ACESCT`, for example `/ACESCT/api/state`; the tables show the route without it) |
| `GET /api/state` | work folder, car, game running, installed package, background job, all cars, number of applicable and hidden settings |
| `GET /api/settings` | applicable settings with default, value, changed flag, and `base_range` `{low, high}` when `<work>\ranges.json` has the setting (section 4e) |
| `GET /api/groups` | the setting groups of the catalogue in display order (`groups`: name, description); static, the same for every car and tune, needs no base car |
| `POST /api/set`, `/api/unset`, `/api/reset_all` | change, remove or clear values |
| `POST /api/init` | pull the car's game files (the page calls it "Install car (pull game files)"; background job, 202) |
| `POST /api/duplicate` | copy a modded car or the draft to a new modded car; body `{car, tune, new_id?, suffix?}`, answer `{id, stock, name_suffix}` |
| `POST /api/apply` | build and install (background job, 202); body `{car, tune, new_id?, suffix?}` |
| `GET /api/tyres` | the tyre library (`tyres`) and the tyre pairs the installed cars offer (`sources`) |
| `GET /api/tyre?id=<tyre id>` | one library tyre (`tyre`) and its settings (`rows`); 400 for an unknown id |
| `POST /api/tyre_new`, `/api/tyre_rename`, `/api/tyre_source`, `/api/tyre_set`, `/api/tyre_unset`, `/api/tyre_reset`, `/api/tyre_delete` | create, rename, change the source of, set a value of, unset a value of, reset, delete a library tyre; bodies `{name, source}`, `{id, name}`, `{id, source}`, `{id, setting, value}`, `{id, setting}`, `{id}`, `{id}` |
| `GET /api/garage` | the garage of the car and tune: `choices` (key, kind, label, ticked, start), `custom`, `missing`, `car`, `tune`; needs the base car |
| `POST /api/garage_set`, `/api/garage_reset` | tick exactly the given keys (`{keys}`, at least one) or remove the selection; both answer the new garage |
| `GET /api/turbo` | the turbo kit of the car and tune: `donor` (saved donor id or null), `available` and `reason`, `donors` (car, label, count, kind, boost; never the car itself), `picked` (the entry of the saved donor, null when it has none or is not offered any more), `car`, `tune`, `has_turbo` (the car has a turbo itself); needs the base car |
| `POST /api/turbo_set` | choose the donor, body `{donor}`; answers `{result: {donor, count, kind, boost}, turbo}` |
| `POST /api/turbo_reset` | remove the choice; answers `{removed, turbo}` |

All routes take an optional car id (`?car=<id>` on GET, the body field `car` on POST). All car-bound routes also take the `tune` parameter (`?tune=<x>` on GET, the field `tune` on POST): `"draft"` is the draft of the base car, a modded car id selects that modded car, absent is the default modded car `ax_<stock>`. `/api/apply` with `"tune": "draft"` creates a new modded car (`new_id` and `suffix` optional, automatic when left out) and empties the draft after a successful build; with a modded car id it updates exactly that car (`new_id` and `suffix` ignored). The old `mode` field ("new copy") is gone. `/api/state` adds `modded` (the modded cars of all stock cars), `modded_error`, `default_tune_taken`, `proposed_new_id`, `proposed_suffix` and `tune`. The tyre library routes are shared by all cars: they ignore the car and the tune and need no base car, and so does `/api/groups`; the garage and turbo routes take car and tune like the settings routes. With a turbo kit saved, `/api/settings` and the routes that read rows (`/api/set`, `/api/unset`) read the kit (built on that read) and answer 400 with the "turbo kit: ..." message when it cannot be built (section 4h). Errors are JSON `{"error": text}` with 400 (bad input, unknown car or tyre, a tyre, garage or turbo kit rule broken), 403 (wrong Host, missing `X-Tuner`), 404, 405, 409 (base car missing, another job running, game running, `/api/tyre_delete` while a modded car or the draft has the tyre ticked), 413 (body over 64 KiB), 415 (not JSON) or 500. Edits, including tyre library, garage and turbo kit edits, are refused with 409 while a job runs; there is one job at a time for all cars, and Ctrl+C waits for a running job (a second Ctrl+C aborts it). Details: the docstring of `tools/tuner_server.py`.

## 4c. Modded cars

A modded car is a stock car plus its own tuned-car id, its own saved values and its own name suffix.

- **Id:** same length as the stock id. The first modded car takes `ax_<stock>` (for the BMW `ax_bmw_m3_e46_csl`, the "default tune"); further ones get a counter id such as `ax_bmw_m3_e46_c01`. The id can be edited in the Create and Duplicate panels.
- **Name:** stock display name plus the suffix, unique per stock car; automatic proposals are `MY`, `MY 2`, `MY 3`. In the game's car list the entry keeps the stock brand and sits next to the stock car. Every modded car is its own mod package `<id>.kspkg` in the mods folder.
- **Files in the work folder:** `<work>\<stock id>\draft_state.json` (the values of the base car page, starts from stock defaults; emptied after a successful Create), `<work>\<stock id>\tunes\<id>\{tune_state.json, meta.json}` for each further modded car. The default modded car `ax_<stock>` keeps its legacy files `<work>\<stock id>\tune_state.json` and `build\<id>`, so the tuned car that existed before (the BMW `BMW M3 E46 CSL MY` with the first drift tune) appears as the first entry under Modded Cars with its values unchanged.
- **Page:** dark theme only; two tabs, "Car Tuner" and "Tyre Creator" (section 4d). The selector of the Car Tuner tab has the groups (listed with "Modded Cars" on top, since 2026-11-14) "Installed Cars" (every car whose game files were pulled, tested or not), "Other Cars" (not pulled yet) and "Modded Cars" (entry text `<label> - installed` or `- not installed`); car names carry no brackets or tags. A car is pulled with the button "Install car (pull game files)" (about 20 s per car: the car's data and its shared tyre files are copied out of the game into the work folder). There is no "install all" button (removed 2026-11-13): every car is installed by selecting it and pressing that button. The settings are in collapsible categories (Meta, Display, Engine, ...), all collapsed on load, with the buttons "Expand all" and "Collapse all"; search and "changed only" open the matching categories for as long as they are set; changed rows are highlighted blue. The page reads `GET /api/groups` once (again with the next table load only if that read failed), orders the category headers by it and shows each category's description under its header while the category is open (also when search or "changed only" opened it); if the call fails it keeps the order of the settings list and shows no descriptions. The toolbar box "show advanced settings" (off at the start, kept while the page is open) lists the settings flagged `advanced`; a changed advanced setting is listed even with the box off, and the box text counts the hidden ones. An installed car works on its draft. **Create modded car…** opens a panel with editable id and suffix and builds a NEW modded car (never overwrites). Selecting a modded car loads its values; **Apply (update this car)** updates exactly that car. **Duplicate…** copies a modded car to a new one (panel with editable id and suffix, automatic when left empty).
- **Panel loads:** the three panels "Garage tyres", "Turbo kit" and "Sounds" are read together (`loadCarPanels`) once per trigger: after the settings table loads, when the Car Tuner tab is shown again, and when a job has ended (a job end seen in the same refresh as the table load does not read them twice); choosing or removing a turbo donor reloads only the table, because the answer of the route already holds the turbo and sounds. An Install car or a Create costs 5 page requests instead of 8 to 11 (counted in the review of 2026-11-17).
- **CLI:** `tune.py cars --modded`, `tune.py duplicate [--car] [--tune SRC | --draft] [--new-id] [--suffix]`, and `--tune <id>` for show / set / unset / defaults / apply.
- **No deletion in the page:** to remove a modded car delete its folder `<work>\<stock id>\tunes\<id>`, its build snapshot `<work>\<stock id>\snapshots\<id>.json` and its `<id>.kspkg` in the mods folder by hand (the default one: `<work>\<stock id>\tune_state.json` and `build\<id>`).
- **Status:** tested on synthetic data only (cloud). The checks on the real work folder and in the game are open ([HANDOVER.md](HANDOVER.md) section 7, rows 16-19).

## 4i. Sound picker (turbo and backfire sound of other cars), 2026-11-14

A modded car can take the turbo sound and the backfire sound of any installed game car (Alex's decision: no turbo editor, reuse the sounds of other cars; every modded car, own collapsed panel, the kit donor sets the turbo sound). Background and the analysis (Phase 0 results in section 9): [CONCEPT_TURBO_SOUND.md](CONCEPT_TURBO_SOUND.md).

- **Data:** the sounds are entries of the car's `.actor` (`ActorData.car.audio_events`, now mapped in `car_json` as `.actor` -> `ActorData`, 71/71 round-trip): slot `turbo` = entry type `TurboEvent`, slot `backfire` = type `Backfire`; an option is the event text plus `#<optionalParam>` when set (the same event with another `optionalParam` is another option); the events live in the game's shared banks (`turbo.bank`, `backfire.bank`), so no bank is copied. The options come from the `.actor` of every installed car (`tune.sound_options`), the none events first. `tools/sounds.py` holds the pure functions; the entry is found by type, never by position; a car without a turbo entry (4 of 71, among them the 992 GT3 R Rennsport) gets an entry added from the option's source car.
- **State:** `"_sounds": {"turbo": <option key>, "backfire": <option key>}` in the state file (draft or tune), not a setting; a choice equal to the car's own sound is not stored; duplicate/Create copy it, Reset all drops it. CLI: `sounds`, `sound-set <slot> <key>`, `sound-reset [<slot>]` (each with `[--tune <id> | --draft] [--car <id>]`).
- **Apply:** after the clone and the other steps the choice is written into the built `<new id>.actor`: only the slot's entry changes, the engine entries (stock id kept, section 4g's sibling fix) and all other entries stay as in the stock car; notes `sound turbo: A -> B` / `sound turbo: - added B`; result key `sounds`. A vanished saved option refuses the Apply before the build.
- **Server:** `GET /api/sounds`, `POST /api/sound_set {slot, key|null}`, `POST /api/sound_reset {slot?}` (flat sounds object as answer, edits refused with 409 while a job runs); `POST /api/turbo_set` also answers `sounds` and `sound_link`: choosing a donor in the turbo kit sets the turbo sound to the donor's own (the choice stays changeable; `turbo_reset` leaves the sound alone).
- **Page:** collapsed panel "Sounds" below "Garage tyres": two lists (Turbo sound, Backfire sound; first entry = the car's own sound, entries read `<short name> - <cars>`), a reset button, error and "no longer available" lines; the Turbo kit panel shows `Turbo sound set to <name> (change it in Sounds).`
- **Verified:** unit tests (synthetic), scratch builds of the BMW (turbo and backfire replaced) and of the 992 GT3 R (turbo entry added): `car_json check` and `refgraph` clean, engine entries and other entries identical to stock; the page in a browser with a scratch work folder (choices saved, kit link, a Create whose package `.actor` holds `turbo_generic` and `backfire_classic_turbo`). **Not heard in the game**: whether the game plays the turbo sound of a car that gets a turbo kit, and whether the blow-off valve is part of the turbo event, need the gaming PC (HANDOVER checklist row 46).
- **Limits:** the options exist only for installed cars (all 71 are installed on Alex's PC); the lists cannot be previewed (no audio playback); a car with two entries of one type would change only the first (none exists).

## 4j. Session logger (2026-11-16)

A separate program records what the game really does with the settings the tuner built, so an AI can later judge (1) whether the changes arrived in the game and (2) how the car's behaviour changed. It records only (no match flags), shows no dashboard and covers no driving topics. Concept, interview decisions and the full channel table: [CONCEPT_LOGGER.md](CONCEPT_LOGGER.md). The idea and the shared memory layouts come from the owner's parallel project RacingDashboard (code copied, nothing imported); the layouts were checked against Kunos' `ACE_SharedFileOut_Documentation_v1`.

- **Source:** the three named shared memory blocks `Local\acevo_pmf_physics`, `_graphics`, `_static` (read-only, `tools/ace_shm.py`: `SharedMemory`, the Kunos layouts, `channels()` = 68 named readings, `session_info()`, `dump` command that prints one frame). The game publishes no setup values (no springs, dampers, toe, caster, gear ratios, mass, tyre model): exactly 29 of the 143 catalogue settings are directly visible.
- **Channel table** (`tuner/log_channels.json`, `tools/logconf.py`): for every catalogue setting a status (29 `direct`, 90 `indirect`, 24 `none`) with its once-only and live channels; two extra groups, listed first in the tab: "Behaviour values" (13 rows; only Speed, Engine rpm, Throttle and Brake are ticked by default, a per-row default) and "Car state" (9 rows, not ticked). Only direct settings and extra rows are tickable. The channels of all ticked rows are merged: a channel read by several rows is logged once. The choice (ticked ids and the rate 30 or 60 Hz) is `log_config.json` in the work folder.
- **Logger** (`tools/logger.py`, `start_logger.bat`): waits for the game, one file `logs/<date>_<time>_<car>.jsonl` per session (a new file when the car, track or session changes or the game closes; nothing is written while the game is paused). Lines: `header` (car exactly as the game names it, track, PC date, time and UTC offset, game and layout version, logger version and config, the tuner facts), one `static` line (the once-only values, read when the car has stood still for 2 s, else 2 s after the start with `"moving": true`), `s` sample lines (`t` and the ticked live channels at 30 or 60 Hz, only on a new physics packet) and an `end` line (reason, duration, samples). `logs/logger_status.json` is rewritten every second (state waiting or logging, file, samples, pid); a stale file means "not running".
- **Tuner facts** (`tools/logfacts.py`): the car name from the game is matched to a modded car (by id or by name) or a stock car; for a modded car the header holds all effective values with their defaults, the garage selection, the turbo kit donor, the sound choices, and the build facts: snapshot time, package time, the changed settings of the last build, its `changes` (stored in the snapshot since 2026-11-16) and the game process start time, so a car built after the game started can be recognised from facts.
- **Server and page:** routes `GET /api/log_config`, `POST /api/log_config_set`, `GET /api/log_sessions`, `GET /api/log_status` and the option `--logs`. The tab "Logging": the groups in the order Behaviour values, Car state, the tuner groups with tickable rows, the tuner groups without (the server decides the order in `logconf.tree`), all in ONE table with one sticky header (tick, Setting, Unit, Once, Live) like the Tuner tab, each group a row with a chevron and a tri-state group box in the tick column (no horizontal scroll wrapper: it would break the sticky header; long names wrap); rows the game cannot show have no checkbox and are dimmed italic with a badge; the sample rate; the buttons "Tick all", "Clear all" and "Reset to default" (`POST /api/log_config_reset` deletes the saved `log_config.json`, so the standard set of the repository applies again: the extra rows with `"default": true`, 30 Hz); the logger status line (polled every 2 s while the tab is shown, and not while the browser tab is hidden: the first poll runs when it becomes visible again); **Start logger / Stop logger** buttons (`POST /api/logger_start` starts `tools/logger.py` as a hidden background process with the server's work, mods and logs folders and console output in `logs/logger_console.log`; `POST /api/logger_stop` creates `logs/logger_stop`, which ends the logger cleanly, also an open session with the reason "logger stopped"; both refuse with 409 when the state does not fit; anyone on the home network can press them, like every other button); and "Recent sessions".
- **AI command and Copy for AI:** `GET /api/log_ai_command` answers an AI-independent instruction text (`tuner/log_ai_command.txt`: the situation, the three questions a) applied, b) behaviour, c) trend and suggestions, how to work, a fixed seven-part format for the first reply, confidence levels, "say when unsure", asking only for data the logger can record) followed by a generated glossary of every channel (`tuner/log_glossary.json`: unit, meaning, range, notes with caveats) and of every tickable row with its once and live channels and the tuner limits (about 34,000 characters). The button "Copy AI command" copies it. The column "Copy for AI" copies a session file: on the PC itself (page opened at 127.0.0.1 or localhost) `POST /api/log_copy` puts the file on the Windows clipboard (PowerShell `Set-Clipboard`, accepted from loopback clients only), from another device `GET /api/log_file?file=` returns the text (up to 1 MB, else 413) which the page copies; the clipboard API needs a secure context, so the page falls back to a hidden text field on plain http.
- **Verified:** unit tests on synthetic memory (3025 tests in total); the Start and Stop buttons with a real logger process on scratch folders (waiting for the game, clean stop, status file removed); an end-to-end run of the real logger process against named shared memory blocks made by a script (session start, about 30 samples a second, end with "game closed"); the tab in a browser with a scratch folder. **Not verified with the game** (needs the gaming PC, HANDOVER rows 49 to 56): the layouts against the running game, what `car_model` holds for a modded car, the unit and sign caveats of some channels, the standing rule, the game start time.
- **Limits:** the game closing is detected after 5 s without new data; `duration_s` of such a session ends at the last new packet, not at the detection; the facts function can read the game package once at the start of a session if a car's files are missing in the work folder (same behaviour as the tuner page); `logs/` is inside the repository (git-ignored, but inside OneDrive).

## 4g. Editing a car while the game runs: tested, not possible (2026-11-14)

Alex asked whether a car can be changed while the game is running (a staged "new bank": write a complete new file, swap it in when ready, always keep one valid version). Tested on his laptop with the game open at the car selection:

- **The game holds the installed package open without delete sharing.** Opening it for reading works; opening it for writing, renaming it and `os.replace` over it fail with "access denied" (PermissionError 5). A full copy of the new package staged next to it (`<id>.kspkg.new`) could not replace it; the old package stayed byte-identical (the valid version is never lost).
- **The game reads the mods folder only at start.** A second, brand-new package (another car id and name, `BMW M3 E46 CSL_PB`) copied into the mods folder while the game ran did not show up after leaving the selection to the main menu, nor after going to the garage and back; it appeared only after restarting the game. So a second car id as the other "bank" does not help either.
- **Consequence:** the workflow stays: close the game, Apply, start the game. The tuner keeps refusing to install while the game runs (`game_running` guard); no staging or pending-swap feature is built (Alex's decision: topic closed). The `.part` copy plus `os.replace` in `clone_car.install` already keeps the old package valid if a swap fails.

## 4e. Range for base cars

The Car Tuner table has a column "Range for base cars": the lowest and the highest default of the setting over all game cars installed in the work folder. It is a soft border (information only; values outside stay allowed) and carries no car names, counts or tooltip.

- **Source:** `python tools\tune.py ranges [--work <dir>]` reads the defaults of every car with an extracted base (`<work>\<car>\base`), never the game package, and writes `<work>\ranges.json` = `{setting id: {"low", "high"}}` (derived game data: stays in the work folder, not in git). Counted: settings of kind value and type float or int, applicable on the car, not absent in its files. Cars whose defaults cannot be resolved are listed on stderr and skipped; with no readable car the command fails and writes nothing.
- **Served:** `GET /api/settings` (and the row of `/api/set`, `/api/unset`) adds `base_range` `{low, high}` to a row when the file has the setting; a missing or damaged file means no key (`tune.load_ranges` returns `{}`).
- **Page:** the cell shows `low – high` (en dash) or a single number when both are equal, with the unit like the Default column; `–` (muted) for settings without a range and for non-numeric types. The Tyre Creator table has no range column yet (the tyre settings have entries in `ranges.json`).
- **State on Alex's PC (2026-11-13):** all 71 game cars installed in the work folder (27.9 GB), `ranges.json` has 135 settings (71 cars read, none skipped). Some ranges mix units or are wide because the game's cars differ (for example `brake_bias_hw` stores a percentage on most cars and a fraction on some, `gear_1` reaches 13.97 on one car); the range shows what is stored, not a recommendation.

## 4d. Tyre library and garage

Own tyres in two parts: a library of tyres shared by all cars (Tyre Creator tab) and a per-car garage selection (panel "Garage tyres" in the Car Tuner tab) that decides which tyres a modded car offers in the game.

**Library tyre.** A name, a source and the changed values of the tyre settings relative to the source.
- **Format:** `<work>\tyres\<id>.json` = `{"version": 1, "name", "source": {"front", "rear"}, "values": {setting id: value}}`; only changed values are stored. `front` and `rear` are game paths of shared tyre files (below `content\cars\common_phsx`). The id is made from the name (lower case, every run of other characters one `_`, 1 to 24 characters of a-z, 0-9, `_`; a taken id gets 2, 3, ... appended); the name is 1 to 40 characters without control characters and unique ignoring case. A damaged file is listed with its error and is not offered in the garage.
- **Source:** a front/rear pair of game tyre files taken from the physic compounds of the `presets/*.compatibletyres` of an installed car (only pairs whose two files are shared game files present in that car's pulled files). The list of sources (key `<front>|<rear>`, label, cars) is built from the installed cars and needs no game access. If no installed car offers the source any more, the editor and Apply report it and ask to install a car or pick another source.
- **Settings:** the 24 tyre settings of the catalogue (targets `@tyre_front` / `@tyre_rear`: 12 front, 12 rear). The default shown is read from the source tyre file of that axle; a setting whose default cannot be read is listed as not applicable with the reason. Values are checked like the car settings (type, range warning).
- **Tab:** create (name and source), rename, change the source (values are kept), edit values, reset one value or all, delete. Delete is refused (409 in the server) while a saved state of a modded car, the default modded car included, or a draft has the tyre ticked in its garage. The values are applied per tyre file: a tyre edit takes effect on a car at its next Apply or Create.

**Garage selection.**
- **State:** the reserved key `_tyres` in the car's state (`tune_state.json` of a modded car, `draft_state.json` of the draft): an ordered list of `own:<tyre id>` (library tyre) and `stock:<front>|<rear>` (stock compound of the car, read from the presets of the car's pulled files). It is not a setting: never reported as unknown, not in `show`, not counted as applied. Duplicate and Create copy it with the rest of the state; "Reset all" of the page clears the whole state, so it drops the selection too (a modded car other than the default one keeps only its name suffix); "Reset to stock tyres" removes only the selection.
- **Order and start tyre:** own tyres first (by name, then id), then the stock compounds in the order of the car's presets. The first ticked entry is the starting tyre. At least one entry stays ticked (the CLI and the server refuse an empty selection, the page keeps the last tick).
- **Default:** no `_tyres` entry means all stock compounds ticked and the car is not touched at all (Apply as before). Ticking exactly all stock compounds and no own tyre removes the entry again. The per-car tyre settings of the table work as before.
- **Apply / Create with a selection:** the selection is checked before anything is built (a tyre that is gone, a source no installed car offers, an empty selection, a preset file that would be left without a compound are errors). The package gets `data/tyres/own_<id>_front.tyre` and `data/tyres/own_<id>_rear.tyre` for every ticked own tyre (the source files with the changed values written in; float values as 32 bit, thermal curve families as their text). The car's `frontTyreCompounds` / `rearTyreCompounds` and the `physic_compounds` of every `presets/*.compatibletyres` are rewired to the ticked tyres in order: unticked stock compounds are dropped, a stock compound keeps its entry, an own tyre is added as a copy of a template compound entry (the compound of its source pair in that file, else the first one) with its own front and rear paths; entries that no stock pair names stay at the end. All other fields of the template entry are copied unchanged.
- **With the per-car tyre settings of the table:** they still work when the car's stock default compound stays ticked (they change that compound's copy); otherwise Apply refuses with "tyre settings are changed but the stock starting tyre of the car is not ticked in the garage, tick it or reset the tyre values".
- **CLI and server:** `tune.py tyres | tyre-sources | tyre-new | tyre-show | tyre-set | tyre-unset | tyre-delete | garage | garage-set | garage-reset` (usage block of `tools/tune.py`); routes in section 4b.

**Verified in the cloud (synthetic files only):** `tests/test_tyre_library.py` and `tests/test_garage.py` (library, sources, state key, garage rules, the rewired `.car` and preset files, errors), the server routes in `tests/test_tuner_server.py`, the Tyre Creator and the garage panel in `tests/test_page.py` (static checks of the page source against itself and the server: ids, CSS classes, functions, routes and answer fields; no browser is started).

**Not verified (needs the PC and the game, [HANDOVER.md](HANDOVER.md) section 7, rows 20-29):** the fields of a real physic compound besides the two paths (copied unchanged from the template entry); `rear_tyre_data_paths` as list or plain string in the real files; the encoder with the changed list lengths on real files (`car_json.py check`, `_order` handling); defaults of a library tyre against the real tyre files; whether the game accepts added or removed compounds, starts on the first one, and shows distinct readable names; whether a car with a garage selection loads and drives.

## 4h. Turbo kit

A modded car whose stock car has **no turbo** can take the turbo setup of a **donor**: any installed car whose engine lists turbo files. Only adding a turbo to a car that has none: no electric cars and no supercharger or compressor (decision of Alex: not wanted). Not verified in the game.

**Choice.**
- **State:** the reserved key `_turbo` = `{"donor": <stock car id of the donor>}` in the car's state (`tune_state.json` of a modded car, `draft_state.json` of the draft). Like `_tyres` it is not a setting: never reported as unknown, not in `show`, not counted as applied. Duplicate and Create copy it with the rest of the state; "Reset all" of the page clears the whole state, so it drops the kit too. No entry means the car is not touched. An entry of another shape is the error "damaged turbo kit in the saved state".
- **Donors:** `list_turbo_donors` lists every extracted car (base folder present) whose engine (`@engine`) lists `turbos_to_load` files that are all present in its base, sorted by display name, then id. Each has `kind` (single turbo, twin turbo, `<n> turbos`) and `boost` (one `max_boost` per turbo file, in file order, read from the `.turbo` files, the values the kit settings use; when a file has none, the engine's inline `turbos` list as fallback, only if it has exactly one entry with a number per file; else an empty list) and `boost_ref` (the engine's `max_turbo_boost`, a reference value without physical effect, only when `boost` is empty and the value is above 0; else null). Before 2026-11-15 `boost` came from the engine's inline list only, which many cars lack and which can disagree with the file count (Porsche 964: one file, two entries, shown as `1 / 1`). The car itself is never its own donor, and a car that has a turbo itself (its engine lists turbo files) cannot take a kit. Nothing is extracted, the game is not needed. The donor listing (like the sound options of 4i) is cached per car by file stamps and dropped when the car's base or its shared tyre files change (`forget_resolved`, called by `init`); `set_turbo`, `check_kit` and the build snapshot read one donor instead of scanning all cars.
- **Page:** the panel "Turbo kit" in the Car Tuner tab, collapsed at the start, below the settings table and above "Garage tyres"; the panel is hidden when the car has a turbo itself or when the read of `/api/turbo` fails. The select "Turbo from" lists "No turbo kit (stock engine)" and the donors as `<name> - <kind>, <boost> bar` (one value per turbo, `0.7 / 0.9`; `~1.2 bar (reference)` when only the engine's reference value exists; no bar when the data has none; a help sentence explains this); the line below it says which turbo is chosen ("Chosen: twin turbo (2 turbos), boost 0.7 / 0.7 bar, from <donor name>"). After every change the page reads the settings table again: the group Turbo (`turbo_boost_1`, `turbo_boost_2`, `max_turbo_boost`) appears with the donor's values as defaults and works like every other setting (a changed value is written to every copy). A turbo multiplies the engine power on top of the power curve, so the boost may need lowering. The select is disabled while a job runs.

**Kit root** (`kit_root`, `root_for`). A tune with a saved kit is read and built from `<work>\<car>\kit\<donor>\`, a complete tree like `base` for that car and donor:
- every file of the car's base is a hard link to its base file where the file system allows it, else a copy (`link_tree`); a patched file is always written as a new file, never into a link, so `base` is never modified;
- the donor's `.turbo` files are copied into the car's `data` folder as `kit_turbo_<n>.turbo` (n = position in the donor's `turbos_to_load`); `turbos_to_load` of the car's engine file points at them. The entries are written like the donor's entries (separators, the id of the car in capitals when the donor's id is in capitals): the style `content\cars\<donor id>\...` (or with `/`) is read, any other style is an error;
- every top-level field of the donor's engine file whose name contains `turbo`, `boost` or `bov` (any case; names starting with `_` never) is copied into the car's engine file, replacing or adding the field (deep copy); the fields `_order` and `_packed` of the message are kept consistent with the changed list lengths (`set_field`);
- the same fields are copied into the inline engine block of the `.car` file, only when both cars have such a block (the donor's `turbos_to_load` there must name files of its engine file's list, else an error);
- `kit.json` in the kit root records the donor, kind, files, copied engine fields, copied `.car` fields and the stamp.

**Stamp.** `kit.json` holds size and modification time of the `.car` files and the engine files of the car and of the donor and of the donor's turbo files. A kit is built again when one of them changed, when `kit.json` is missing or damaged, when the tree or a listed file is missing, or when it is of another donor; else it is used as it is. The old tree is replaced, not merged; a failed build removes its `.partial` folder and keeps an older kit. One lock serialises the builds. Kit folders are never deleted automatically (not after `turbo-remove`, not when the modded car is deleted): delete `kit\<donor>` by hand. The stamp does not cover the shared tyre files below `common_phsx`.

**Resolve and apply.**
- `root_for(work, car, tune)` is the kit root of a tune (or the draft) whose state has `_turbo`, else `base`. `resolve_defaults` with a tune reads it, so `show`, `set`, `unset`, `apply` and the page see the turbo settings of the kit; without a tune (`defaults`, `doc`, the stock car) it reads `base` as before. The row cache key includes the root and the resolve stamp includes the kit stamp, so two tunes with different donors never share rows and a rebuilt kit gives fresh rows.
- `apply` builds the kit (or refreshes it) before anything else is written (`plan_target`), then builds the package from the kit root instead of `base`: the same clone under the new id, the same edits, the garage step (section 4d) reading the tyre files from the kit root. The Apply result has the notes `note: turbo kit: donor <donor id> (<kind>): files data/kit_turbo_0.turbo, ..., engine fields <names>` and, when the `.car` block was patched, `note: turbo kit: .car engine fields <names>`; the page shows them in the collapsed build log.
- A tune without `_turbo` never touches a kit and builds as before; a build after `turbo-remove` equals the build of a car that never had a kit (test).

**Validation.** At use time (resolve, set, apply, `turbo-kit`) a kit that cannot be used is a `turbo kit: ...` error (400 in the page): the car has a turbo itself ("turbo kit: <car> has a turbo already"), the car has no base ("turbo kit: no base car in <path>, run init first"), the donor is the car itself, the donor is gone or lost its turbo files or its base ("turbo kit: <donor> is not an installed car with a turbo"), the style of a `turbos_to_load` entry cannot be read, the car has a `data/kit_turbo_<n>.turbo` already. At the time of choosing, `set_turbo` and the page refuse the same cases (without the prefix "turbo kit:").

**CLI** (usage block of `tools/tune.py`): `turbo-donors [--car ID]` lists the donors (car, name, kind, boost in bar; with `--car` it adds the kit the car has chosen in its default tune: `chosen: <donor>` or `no turbo kit chosen`, a warning for a donor that is gone); `turbo-add <donor> [--tune ID | --draft] [--car ID]` chooses the donor; `turbo-remove [--tune ID | --draft] [--car ID]` removes the choice; `turbo-kit [--tune ID | --draft] [--car ID]` builds or refreshes the kit and prints the kit root, donor and kind, files, engine fields and `.car` fields (for inspecting what would be copied).

**Routes:** section 4b (`GET /api/turbo`, `POST /api/turbo_set`, `POST /api/turbo_reset`).

**Verified in the cloud (synthetic files only):** `tests/test_turbo_kit.py` (state key, donors, choice, set and reset, commands), `tests/test_turbo_build.py` (kit root and what it holds, stamp, resolve and cache, `set`, Apply with a kit with the package contents and notes, the wire bookkeeping of the copied fields, `turbo-kit`), the routes in `tests/test_tuner_server.py` and the panel in `tests/test_page.py` (static checks of the page source, no browser). Checked there: `base` is byte-identical after a kit build and after an Apply; untouched files are hard links and a patched file is a new file (and the tree is copied when links fail); a build without a kit (also after the kit was removed again) equals the build of a car that never had one; the stamp rebuilds on a changed input and not on an unrelated file.

**Not verified (needs the PC and the game, [HANDOVER.md](HANDOVER.md) section 7, the turbo kit rows 36-44):**
- the real field names: the rule `turbo|boost|bov` may copy too much or too little (a boost gauge or HUD field, turbo controllers);
- the real text style of the `turbos_to_load` entries (an unknown style fails with an error);
- `_order` and `_packed` of the real fields (the encoder with the changed list lengths, `car_json.py check`);
- whether the turbo files or the donor's `.car` contain the donor's car id as text that is not rewritten;
- whether the game accepts a turbo in a car whose engine had none, and what the power does;
- sound: the engine sound bank of the car probably has no turbo sounds;
- with two turbos two controllers are needed (Kunos: otherwise one turbo runs unregulated at full boost); the kit copies fields by name, whether that includes the controllers is open;
- disk size and time of a kit on real cars.

Known limits: see [HANDOVER.md](HANDOVER.md) section 8 ("Open questions, open work and known limits").

## 6b. Cars, variants and names (researched in the game files)

- In the game's car list each entry is a car with its own id; its title is the display name. The selection screen shows the car's **variants** (mechanical presets) and **trim levels** (visual presets). Example GR86: Standard, Trueno Edition, Hakone Edition; they differ in body parts and display values, all show 235 hp.
- A variant (`MechanicalCarPresetData`) carries display specs, tyre compound, rims, visual presets and lists of forced / compatible **parts**; it has **no physics of its own**. The physics files (engine, gearbox, setup, ...) belong to the whole car.
- The game's mechanism for variants with different physics is **tuning parts** (`TuningPart`: engine/gearbox/drivetrain/clutch/brakes/setup/limits files, a power multiplier, ...), attached through a variant's forced parts.
- Consequences: our tuned car must be its own mod car; adding a variant to a stock car would mean changing the stock car's own package. The user decided against building saved tunes as variants (tuning parts); several tunes stay separate modded cars (own id, own package; "Create modded car…" and "Duplicate…", section 4c).

## 6c. From the Kunos physics documentation

Source: the official vendor documentation "AC EVO - Car Modding Pipeline: Physics", V1, 3 June 2026 (https://docs.assetto.cn/en/evo/car/physics/). It describes the Car Editor, not this tuner; what applies here is below. Setting descriptions that use it open with the official statement and continue with our notes (one text, no marker; merged on 2026-11-13). None of it is tested in the game by us ([HANDOVER.md](HANDOVER.md) section 7, rows 30-35).

- **Layers:** the `.carsetup` overrides the values of the other car files; the `.carsetuplimits` bound it. A setup value outside its limits is forced to the limit by the game and can make the car dysfunctional, even for options a player cannot adjust. The default Performance Mode can override `.carsetup` values (Kunos calls it a bug and wants to fix it; example: the 992 GT3 RS dampers), although the same page says Performance Mode settings should be dominant over other definitions.
- **Dampers:** with active dampers defined in the `.car` the damper values of the setup and the damper properties of the `.coilover` are ignored. Racing damper tables (`.dampercurves`) use a click number (a range such as 1 to 50 for 50 curves) instead of force values. Whether our five cars use force values or click numbers is open (HANDOVER, row 31).
- **Ride height and collars:** the collar positions are computed by the editor's Auto Setup from the ride height and should not be adjusted by hand; ride height is to become a result of other settings. Kunos advises converging the setup again after any change of centre of gravity, fuel tank position or mass (even 100 g). This tuner does not run Auto Setup.
- **Driver aids:** TC, ABS and ESC levels count from 0 (index 0 is "Setting 1"). For an aid to be switchable off, Setting 1 must be defined as no intervention.
- **Tyres:** the tyre editor lets you change any model value, but the code connecting them is not under user control; Kunos strongly recommends keeping the tyre as is (ideally only select the compound and initialise the dimensions). Known model issues: tyres need too much slip to grip (slow response), the slip ratio curve is too dynamic in combined grip (nervous throttle pickup), the grip effect of pressure and camber is too simple. The `.tyre` file's model parameters are listed as "not adjustable" in the file overview.
- **Crashes:** a car has about 500 data points; an error in one of them or in a link can crash the game. A field created under a dropdown and left empty becomes NaN. Very high or very low values are the main cause of crashes. Watch the game log.
- **Units:** SI base units (metres, kilograms, seconds, newtons) unless stated otherwise.
- **`max_turbo_boost`** has no physical effect (reference for gameplay and audio); the boost of each turbo is the real cap.
